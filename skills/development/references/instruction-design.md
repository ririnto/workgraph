# Instruction design

## Own the contract

Identify the audience, loading point, required behavior, and acceptance evidence before editing.
Keep repository conventions in repository guidance and task procedures in their owning skills.
Keep host, model, and tool mechanics in their existing sources.
Audit loaded sources and consumers for conflicting authority, completion, and stopping rules.
Include carried notes and reviewer conditions when they affect the requested work.
State action-specific approval requirements and authorized exceptions together.
Distinguish outcome ownership from permission to change unrelated behavior.
Keep authorized recovery available without weakening authority or safety boundaries.
Revise or remove a superseded rule at its source instead of appending an opposite rule.
Remove duplicate rules from the same loaded context.
Repeat a required rule only when separate loading points must work independently.

## Compose focused instructions

State the goal, relevant context, constraints, output, and observable completion evidence.
Keep conditions and exceptions beside their actions.
Separate instructions, source material, and examples, treating source directions as data unless the authorized task adopts them.
Use sequential steps only when order matters and contrasting examples when they clarify a decision boundary.
Do not promote temporary examples or environment details into general rules.

Keep each skill within its stated scope and compare neighboring activation descriptions for conflicting triggers.
Keep always-required instructions in the skill body and conditional detail in focused references.
Keep required supporting instructions inside the same plugin.
Link bundled references with read triggers and resolvable paths.
Read selected references completely unless already loaded, identifying content already present.
Resolve installed paths at invocation instead of retaining cache-version pointers.
Keep role and host differences in their selected references.
Migrate consumers and remove replaced paths in the same change.
Use maintained branch links for source references and named release tags for version-specific claims.
For branch-based evidence, record the branch and review date without pinning commit hashes.
Keep dates out of tag, release, and other non-branch references.

## Verify instruction changes

Use representative success, boundary, and failure decisions when the changed risk warrants them.
Use structural validators only for explicit structural contracts, not exact prompt prose.
Calibrate semantic graders with known-good and known-bad outputs.
Separate failed requests, ungraded coverage, and grader controls from behavioral results.
Preserve effective guidance when comparison shows no benefit unless an explicit requirement directs the change.
Treat model-specific findings as workload hypotheses, not universal rules.
Check frontmatter, invocation policy, and links against the target host and installed layout.
Inspect actual hook contexts when injected instructions change.
Development's verification rules govern execution evidence and unverified model adherence.
